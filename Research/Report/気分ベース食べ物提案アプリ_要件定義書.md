# 気分ベース食べ物提案アプリ 要件定義書（ドラフト）

本書は `2026-app-trend-research.md` で行った市場調査・技術検証（4-5, 4-6）を土台に、開発着手のための要件を一つにまとめたもの。仮称は「気分ごはん」とする（アプリ名は未確定、12章参照）。

---

## 1. コンセプト

**「今の気分」を伝えるだけで、自炊・惣菜・コンビニ・外食を横断して「今日何を食べるか」を提案してくれるアプリ。** レシートスキャンによる食履歴の自動蓄積を差別化のサブ機能とし、提案の精度と先回り提案に活用する。

「レシピ」に限定しない点、また自炊/外食それぞれに閉じた既存の気分提案サービスと異なり選択肢を横断する点が独自性（詳細は元レポート4-6参照）。

---

## 2. 解決する課題（ペイン）

- 「今日何を食べよう」という日常的な意思決定疲れ。特に自炊する気力がない日に、コンビニ・惣菜・外食のどれにするかも含めて考えるのが面倒。
- 既存の献立提案サービス（おいしい健康、あすけん等）は自炊レシピに閉じており、外食系サービス（ぐるなびUMAME!、食べログ）は外食に閉じている。両者を横断して「今の気分」から選ばせてくれるサービスがない。
- 既存の食事管理アプリは手入力や写真判定が主流で、記録の継続が面倒。

---

## 3. ターゲットユーザー（要確認・4章参照）

一次仮説：自炊とコンビニ・惣菜・外食を日常的に併用する20〜40代の一人暮らし／共働き世帯。「毎日フル自炊するほどではないが、健康や食費も気にしている」層を想定。ペルソナの確定は12章の要検討事項とする。

---

## 4. コア体験・ユーザーフロー

1. ユーザーが気分をチャット欄に自然言語で入力する（例：「さっぱりしたものが食べたい」）
2. LLMが気分を軸（温冷／さっぱり・こってり／辛さ／ボリューム感／和洋中）に沿ってカテゴリ判定する
3. 判定結果をもとに、自炊・惣菜・コンビニ・外食を横断して提案を提示する
   - 自炊：LLMがその場でレシピを生成
   - 惣菜／コンビニ：カテゴリ＋属性レベルで提案（実在の商品名は出さない）
   - 外食：近隣の飲食店をジャンル・評価・口コミの雰囲気でランキング表示
4. （サブ機能）レシートを撮影すると、OCR→LLM正規化を経て「食べたものの傾向（カテゴリ単位）」が自動的に記録される
5. 記録された傾向をもとに、次回以降は気分入力なしでも先回り提案ができる（例：「今週揚げ物が続いているので、今日はさっぱり系はいかがですか？」）

## 5. 機能要件

### 5-1. MVP（v1）に含める機能

| # | 機能 | 設計方針 | 根拠（元レポート） |
|---|---|---|---|
| 1 | 気分チャット入力→カテゴリ判定 | LLM（Claude API）で自然言語をカテゴリ・属性軸に変換。判定が曖昧な場合は一言聞き返す会話設計を入れる | 4-6 技術検証：自然言語→カテゴリ判定 |
| 2 | 自炊レシピ提案 | 固定レシピDBを持たず、LLMがその場でレシピを生成。楽天レシピ／クックパッドAPIのライセンス制約（商用利用不可）を回避 | 4-5 MVP機能の絞り込み |
| 3 | 惣菜／コンビニのカテゴリ提案 | 日本標準商品分類の惣菜8カテゴリ（煮物・焼き物・炒め物・揚げ物・蒸し物・和え物・米飯類・その他）を土台に、実在の商品名を断定せずカテゴリ＋属性で提案 | 4-6 技術検証：カテゴリ→接続可能性 |
| 4 | 近隣飲食店の推薦 | Google Places API（New）でジャンル・評価・距離・AI口コミ要約を取得し、気分カテゴリとマッチする店を提示。メニュー内容までは踏み込まない | 4-6 技術検証：おすすめ店舗推薦機能 |
| 5 | レシート撮影→OCR→カテゴリ記録 | Google Cloud Vision APIでOCR→LLMで「揚げ物系」「麺類」等の大まかなカテゴリへ正規化。精緻な食材名の特定は狙わない（生鮮食品は店舗ごとの表記ゆれが大きいため） | 4-5 技術検証：LLM正規化ステップ／4-6 レシート機能の再設計 |
| 6 | 低信頼度項目のワンタップ確認 | OCR・LLM正規化の確信度が低い項目のみユーザーに確認させ、精度不足を補う | 4-5 MVP機能の絞り込み |
| 7 | 対応スーパーを2〜3チェーンに限定 | 初期チューニング対象を絞る（候補：イオン、ライフ、ヤオコー等）。全国対応は後回し | 4-5 MVP機能の絞り込み |

### 5-2. MVPから外す機能（v2以降）

- 賞味期限管理・食品ロス訴求機能
- 家計簿的な支出管理・グラフ化
- お気に入りレシピ保存・週間献立カレンダー
- 好み学習の高度化（協調フィルタリング等によるパーソナライズ）
- 電子レシート（スマートレシート等）との直接連携（ビジネス提携が前提のため）
- Google Places APIの`businessMenus`を使った飲食店メニュー表示（対応店舗数が限定的なため優先度低）
- コンビニ・惣菜チェーンとの公式提携による具体的商品名の提案

### 5-3. 絞り込みの理由

MVPで検証すべき核心は「気分入力から、選択肢横断（自炊・惣菜・コンビニ・外食）で実用的な提案ができるか」の一点。レシート機能は差別化の要だが技術負荷も高いため、コア価値（気分→横断提案）を先に検証し、レシート機能を後追いで磨き込む二段構えも選択肢として検討する（12章参照）。

## 6. 非機能要件

### 6-1. 対象プラットフォーム

- iOS・Android（本ワークスペースの親リポジトリ`apps/mobile`のExpo/React Nativeスキャフォールドを利用想定。実装は`ALL`リポジトリ側で行う）

### 6-2. 外部API構成

| 用途 | API | 備考 |
|---|---|---|
| レシートOCR | Google Cloud Vision API | 日本語対応。AWS Textractは日本語非対応のため不採用 |
| 気分カテゴリ判定・食材/カテゴリ正規化・レシピ生成 | Claude API（LLM） | 固定辞書・固定DBを持たない設計の中核 |
| 近隣店舗検索・推薦 | Google Places API（New） | 有料の商用サービスのため、サブスク課金モデルと整合。階層制（Essentials/Pro/Enterprise）でコストが変わる |
| （検証用途限定）飲食店ジャンル情報 | ホットペッパーグルメAPI | 無料だが商用利用不可。プロトタイプ検証にのみ使用し、本番では不使用 |

### 6-3. コスト・パフォーマンス

- Google Places APIのEnterprise階層（口コミ取得）は無料枠が月1,000件と少ないため、同一エリア・同一時間帯の検索結果をキャッシュし、呼び出し回数を抑える。
- 楽天レシピAPI、ホットペッパーAPI等の「無料だが商用利用不可」なAPIは本番のサブスク課金環境では使用しない。

### 6-4. 法規制・コンプライアンス

- レシートOCRで得る購買履歴データはプライバシーポリシーでの明示が必要（要配慮個人情報には該当しないが、購買傾向という個人データである点に留意）。
- 実在の店舗名を表示する際、評価・口コミ情報の正確性についてGoogle Places API由来である旨と免責事項を明記する。
- 惣菜・コンビニについては実在の商品名を断定的に表示しない（データ未保有のため、誤情報リスク回避の観点でも必須）。

## 7. 画面構成（ラフ）

| 画面 | 内容 |
|---|---|
| ホーム（気分入力） | チャットUIで気分を入力。過去の食履歴に基づく先回り提案もここに表示 |
| 提案結果 | 自炊／惣菜／コンビニ／外食をタブまたはカードで横断表示 |
| 飲食店詳細 | ジャンル・評価・距離・口コミ要約（Google Places由来の出典表示付き） |
| レシートスキャン | カメラ起動→OCR結果の確認・低信頼度項目の修正UI |
| 食履歴 | カテゴリ単位での傾向表示（例：今週は揚げ物が多い） |
| 設定 | 対応店舗の地域設定、サブスク管理等 |

## 8. データ設計の概要（Phase 1スコープ）

Phase 1（レシート機能なしの気分→横断提案）の範囲でエンティティを設計する。Phase 2（レシートによる食履歴）の拡張ポイントは8-4に記載。

### 8-1. 主要エンティティ

**User（ユーザー）**

| フィールド | 型 | 内容 |
|---|---|---|
| id | UUID | 主キー |
| auth_provider_id | string | 認証基盤の外部ID（Apple/Google/メール等） |
| default_area | geo (lat/lng) | 近隣店舗検索のデフォルト位置 |
| subscription_status | enum(free, premium) | 9章のマネタイズ設計に対応 |
| created_at | timestamp | |

**MoodInput（気分入力ログ）**

| フィールド | 型 | 内容 |
|---|---|---|
| id | UUID | 主キー |
| user_id | UUID (FK) | |
| raw_text | text | ユーザーが入力した自然言語 |
| needs_clarification | boolean | LLM判定が一意に定まらず聞き返しが発生したか（4-6技術検証を参照） |
| clarification_answer | text (nullable) | 聞き返しに対する追加回答 |
| created_at | timestamp | |

**MoodCategoryResult（気分判定結果）**

| フィールド | 型 | 内容 |
|---|---|---|
| id | UUID | 主キー |
| mood_input_id | UUID (FK) | |
| axis | enum(温冷, さっぱりこってり, 辛さ, ボリューム, 和洋中) | 判定軸 |
| value | string | 軸ごとの判定値（例：「さっぱり」「揚げ物系」等） |
| confidence | enum(高, 中, 低) | 4-6の机上検証で用いた信頼度ラベルを踏襲 |

MoodInput 1件に対し、判定軸の数だけMoodCategoryResultが複数紐づく。

**FoodCategoryTaxonomy（食カテゴリマスタ）** ※更新頻度が低いためコード内定数でも可

| フィールド | 型 | 内容 |
|---|---|---|
| id | string | 例：`souzai.agemono`（揚げ物類） |
| channel | enum(自炊, 惣菜, コンビニ, 外食) | どのチャネル向けの分類か |
| label | string | 表示名 |
| parent_id | string (nullable) | 階層化する場合の親カテゴリ |

日本標準商品分類の惣菜8分類（煮物・焼き物・炒め物・揚げ物・蒸し物・和え物・米飯類・その他）＋独自軸（辛さ等）を初期データとして投入する。

**SuggestionResult（提案結果ログ）**

| フィールド | 型 | 内容 |
|---|---|---|
| id | UUID | 主キー |
| mood_input_id | UUID (FK) | |
| channel | enum(自炊, 惣菜, コンビニ, 外食) | |
| category_tags | string[] | マッチしたカテゴリ |
| generated_content | text | 自炊はLLM生成レシピ本文、惣菜/コンビニはカテゴリ提案文 |
| restaurant_place_ids | string[] (nullable) | 外食の場合、下記キャッシュを参照 |
| created_at | timestamp | |

**RestaurantRecommendationCache（飲食店推薦キャッシュ）** — Google Places APIのコスト抑制の要

| フィールド | 型 | 内容 |
|---|---|---|
| id | UUID | 主キー |
| geo_cell | string | 緯度経度を一定粒度で丸めたキー（例：500m四方単位） |
| mood_category | string | どの気分カテゴリに対する検索結果か |
| google_place_id | string | |
| name / genre / rating / review_summary | string等 | Google Places APIからの取得値 |
| fetched_at | timestamp | |
| expires_at | timestamp | キャッシュ有効期限（数時間〜1日程度を想定） |

ユーザー非依存で、エリア×気分カテゴリ単位に複数ユーザー間で共有できるグローバルキャッシュとする。ユーザーごとに毎回APIを叩くと6-3で挙げたEnterprise階層の無料枠（月1,000件）をすぐ使い切るため。

### 8-2. リレーション概要

```
User 1─N MoodInput 1─N MoodCategoryResult
MoodInput 1─N SuggestionResult ─N RestaurantRecommendationCache（参照のみ、非所有）
```

### 8-3. 技術選定への言及（提案）

個人開発の実装コストを考えると、認証・DB・ストレージをまとめて扱えるBaaS（例：Supabase＝PostgreSQL）が候補になる。上記はリレーショナルDBを前提にしているが、これは提案であり確定ではない（12章の要検討事項）。

### 8-4. Phase 2への拡張ポイント

Phase 2でレシート機能（食履歴）を追加する際、`FoodHistory`テーブル（カテゴリ、日時、店舗名任意、金額任意）を新設し、`SuggestionResult`と緩く関連付けられるようにしておくと後方互換が保てる。Phase 1時点でこのテーブルを作る必要はないが、`FoodCategoryTaxonomy`のカテゴリIDを`FoodHistory.category_id`でそのまま再利用できるよう、カテゴリ体系をPhase 1のうちに固めておくことが重要（唯一、Phase 2を見越して今のうちに決めておくべき部分）。

## 9. マネタイズ設計

- **基本方針：サブスクリプション課金。** Google Places APIの従量コストをカバーする必要があるため、無料開放は難しい（元レポート5章・6-3参照）。
- **無料枠（案）：** 1日あたりの気分提案回数に上限を設ける、レシートスキャンは月間◯枚まで、飲食店の口コミ要約表示は有料限定、など。具体的な線引きは12章の要検討事項。
- **有料プラン（案）：** 無制限の提案回数、口コミ要約付きの飲食店推薦、食傾向分析（週次サマリー等）。

## 10. 開発ロードマップ（案）

| フェーズ | 内容 |
|---|---|
| Phase 0：技術検証 | 実際のレシートを対象チェーンで収集し、Google Cloud Vision APIでOCR精度を検証。対応スーパー2〜3チェーンを確定 |
| Phase 1：MVPコア | 気分入力→カテゴリ判定→自炊／惣菜／コンビニ／外食の横断提案（レシート機能なしでもコア価値を検証できる最小構成） |
| Phase 2：差別化機能 | レシートスキャン→カテゴリ単位の食履歴記録、先回り提案の実装 |
| Phase 3：拡大 | 対応店舗の全国展開、パーソナライズ強化、コンビニ・惣菜チェーンとの提携検討 |

Phase 1でレシート機能を外す設計は、開発負荷の高い機能（OCR＋正規化の精度作り込み）を後回しにし、まず「気分→横断提案」というコア価値がユーザーに刺さるかを検証するリーンな進め方の一案。

## 11. リスクと対応

| リスク | 内容 | 対応方針 |
|---|---|---|
| OCR精度 | 感熱紙の劣化・店舗ごとの表記ゆれで正規化に失敗する可能性 | 用途をカテゴリレベルに限定して精度要求を下げる。低信頼度項目はユーザー確認を挟む |
| API商用利用制約 | 楽天レシピ・ホットペッパー等、無料APIの多くが商用利用不可 | 本番はGoogle Places API（有料・商用可）を主軸に据える。無料APIは検証用途に限定 |
| コンビニ商品データの不在 | 個人開発で扱える商品APIが存在しない（IMD社DBは年額200万円〜） | 商品名を出さずカテゴリ提案に留める。提携は将来検討 |
| レシピDB調達 | クックパッド等の公開APIは一般開発者に非提供 | LLM生成方式で代替し、DB保有自体を不要にする |
| 感情語彙の解釈 | 「元気を出したい」等、味の軸が一意に定まらない入力がある | 聞き返しの会話設計を組み込む |
| Places APIコスト増 | 口コミ取得（Enterprise階層）の無料枠が少ない | 検索結果のキャッシュでAPI呼び出し回数を抑制 |

## 12. 未確定・要検討事項

開発着手前にユーザー確認・意思決定が必要な項目。

1. **アプリ名**（本書では仮称「気分ごはん」）
2. **ターゲットペルソナの絞り込み**（3章は仮説段階）
3. **対応スーパー2〜3チェーンの具体的な選定**（イオン／ライフ／ヤオコー等から確定）
4. **無料／有料機能の詳細な線引き**（9章は案の段階）
5. **レシート機能をMVP初期から含めるか、Phase 2に回すか**（10章の進め方案について合意が必要）
6. **開発言語・体制**：`apps/mobile`（Expo/React Native）をベースにするか、新規プロジェクトとして切るか
