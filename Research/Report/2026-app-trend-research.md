# アプリ開発トレンド・需要調査レポート（2026年版）

## 1. 調査の前提
- 開発規模：個人開発（副業）を想定。1〜3ヶ月程度で作り切れる規模感。
- ターゲット市場：日本国内。
- ジャンル：特定分野に絞らず幅広く調査。
- マネタイズ：未定のため、本レポートでモデル別に整理。

---

## 2. 市場全体の動向

- 世界のモバイルアプリ市場は2025年の約3,139億ドルから2026年に約3,576億ドルへ拡大見込み（2030年に約6,025億ドル、CAGR13.9%）。
- アプリ内課金（サブスク含む）市場は2026年に約3,228億ドル規模、CAGR26.2%と課金市場の伸びが特に大きい。
- 日本のサブスク型EC市場は2026年までに約93.4億ドル規模に到達見込み。**単発課金よりサブスク型の方が市場の伸びは大きい**。
- 2026年のアプリ開発トレンドは「AI-Nativeアプリ（AIが中核機能）」「オンデバイスAI」「生成AI統合」「クロスプラットフォーム開発」「5G対応」の5本柱。
- Gartnerは「2026年までに世界企業の80%以上がGenAI API・モデルを利用、またはGenAI対応アプリを本格展開」と予測。

**示唆：** 個人開発でも「AIを中核機能として組み込む」ことが前提になりつつある。ただし後述の通り、AIを載せただけの汎用アプリはレッドオーシャン化している点に注意。

---

## 3. 個人開発を取り巻く環境変化（2026年）

- Claude Code、Cursorなどのバイブコーディング系AIツールの普及により、「コードを書く」ハードル自体は劇的に下がった。
- 反面、「同じアイデアを他の誰かが先にAIで作ってしまう」「類似プロダクトが毎日のように生まれる」という**競争の激化**が進んでいる。
- そのため2026年の個人開発の勝敗を分けるのは、実装力ではなく「誰にどう届けるか」というマーケティング・チャネル設計の質にシフトしている。
- 「汎用ToDoアプリ」「ただのChatGPTラッパー」のような差別化のないプロダクトは、2026年時点で成功確率が極めて低い領域と評価されている。
- AI駆動開発を導入した学習者のリリース到達率は77%（従来の約2.5倍）というデータもあり、「作る」こと自体のハードルは下がっている＝アイデアの独自性と流通設計がより重要。

**示唆：** 「広く浅いジャンルで大きく作る」より、「狭く深いニッチで、明確なペインを解決する」方が個人開発には向いている。

## 4. 需要が見込めるジャンル（分野別）

### 4-1. ヘルスケア・フィットネス系
- 日本のフィットネスアプリ市場は2025年に約1.72億ドル、2026〜2034年でCAGR15.54%、2034年に約6.3億ドル規模へ成長見込み。
- 日本の成人の約60%が積極的に健康改善方法を探しており、ダウンロード数・サブスク登録数の伸びに直結。
- ウェアラブル（スマートウォッチ等）との連携、パーソナライズされたワークアウト・栄養管理、コミュニティ機能への需要が強い。
- **個人開発の切り口例：** 特定の運動種目（マラソン、筋トレの部位特化、ストレッチ等）に絞った記録アプリ／睡眠と連動した体調管理アプリ。

#### 4-1-a. 既存アプリの分類（競合把握）

| カテゴリ | 代表アプリ | 特徴 |
|---|---|---|
| 運動記録（ランニング） | Nike Run Club、Strava、Runtrip、Runna | GPS計測、SNS的共有、AIコーチによる練習メニュー自動作成 |
| 運動記録（筋トレ） | 筋トレ日記型アプリ、Gymny | カレンダー可視化、種目特化型の記録 |
| 総合フィットネス | MyFitnessPal、LazyFit、プランフィット | 運動計画〜食事管理までワンストップ |
| 睡眠記録 | BetterSleep、Sleep Cycle、ShutEye | トラッキング＋音声コンテンツ、眠りの浅いタイミングでの起床 |
| 女性ヘルスケア | ルナルナ（2,300万DL） | 生理・排卵日・基礎体温・PMS・妊活・服薬管理まで網羅する総合型 |

いずれも大手・老舗が強いレッドオーシャンであり、個人開発は「特定種目」「特定属性」「特定症状」に絞った特化型で差別化するのが定石。

#### 4-1-b. ニッチの切り口例

| 切り口 | 理由 |
|---|---|
| 特定種目特化（クライミング、ゴルフの素振り記録、水泳の泳法別記録など） | 総合アプリでは種目固有の記録項目に対応しきれない。愛好者コミュニティの熱量が高い |
| 部位・目的特化の筋トレ記録（肩の可動域改善、産後の骨盤ケアなど） | 「筋トレ全般」より明確な悩みに刺さる方が競合が薄い |
| 睡眠×特定属性（シフト勤務者の不規則睡眠、育児中の細切れ睡眠） | 汎用睡眠アプリが想定していない生活パターン |
| 更年期・PMS・妊活など女性ヘルスケアの症状特化 | ルナルナは総合型のため、特定症状に深く踏み込む余地あり |
| ウェアラブル連携×パーソナライズ通知（姿勢改善、水分補給リマインドなど） | Apple Watch等のデータを使い、より狭い目的に絞る |

#### 4-1-c. 個人開発における規制上の注意点

- 健康情報は個人情報保護法上の「要配慮個人情報」に該当し、通信の暗号化（SSL/TLS）やデータ保管場所の明確化が必要。
- 「診断」「治療効果を示唆する」機能を持たせると薬機法上の医療機器プログラムに該当し、PMDAへの承認が必要になる場合がある。個人開発では**記録・可視化にとどめ、診断的な表現を避ける**のが現実的。

### 4-2. 生産性・習慣化・ライフログ系
- タスク管理・習慣化アプリは競合が非常に多い成熟市場だが、2026年は「ゲーミフィケーション」「ソーシャル機能（他ユーザーとの交流）」「複数デバイス同期」で差別化する流れ。
- ポモドーロ×ToDoのような機能統合型が支持されている。
- **個人開発の切り口例：** 特定の職種・ライフスタイル（フリーランス、育児中、シフト勤務者など）に特化した習慣化アプリ。汎用ToDoは避ける。

### 4-3. AIツール活用系
- チャット・文章生成・画像生成・翻訳・動画音声生成の5ジャンルで人気アプリが乱立しており、ChatGPT自体が2025年に世界で約7.7億回ダウンロードされるなど圧倒的存在感。
- 2026年は「複数のAIアプリを使い分ける」よりも「エージェント型AIに業務を集約する」流れが強まっている。
- **単なるChatGPTラッパーは差別化不能でレッドオーシャン**。勝ち筋は「特定業務・特定業界に特化したAIアシスタント」（例：飲食店の発注メモ作成、フリーランスの請求書AI作成、美容師のカウンセリングメモ生成など）。

### 4-4. ニッチ×トレンドの掛け合わせ型
- 「AI（トレンド）」×「特定の趣味の記録（ニッチ）」、「副業（トレンド）」×「特定スキルの学習（ニッチ）」のように、トレンド要素とニッチ市場を掛け合わせる設計が有効とされる。
- 大企業が参入しにくい「狭く・深く・特殊な」市場を個人開発が取りに行くのが定石。
- **成功事例：** Markdownノートアプリ「Inkdrop」は月額サブスクで月15万円以上の安定収益。開発者自身がYouTubeで開発過程を発信しファンコミュニティを構築（ニッチだが確実なペインの解決＋発信力）。
- **成功事例：** 家計簿アプリ「Zaim」はリリース1年で30万DL、その後950万DL超の大ヒットに成長（生活密着型の継続的ペイン解決）。

### 4-5. ライフスタイル支援系：具体アイデア評価「レシート読込み→レシピ提案」

ユーザー提案アイデアの検証結果。

#### 既存の類似アプリ

| アプリ | 方式 | 特徴・弱み |
|---|---|---|
| レシーピ！ | レシート撮影→家計簿記録→レシピ提案（8,000品目からランダム提示） | 家計簿がメインでレシピは付随機能。**Android限定**、提案が「ランダム」で精度が低い、無料版は広告が多い |
| pecco（ぺっこ） | 食材を手動登録→AIが最適レシピを提案、賞味期限アラート | 50万DL達成。AIマッチング精度は高いが**食材を手入力する手間**がボトルネック |
| クックパッド | 食材名で検索 | 3,800万品のレシピDBで圧倒的支配力だが、レシート連携なし |
| マネーフォワードME／Zaim | レシートOCRで家計簿記録 | OCR自体は成熟技術。レシピ提案には非対応 |

#### レシーピ！の機能・料金体系（詳細）

**機能一覧**

| 機能 | 内容 |
|---|---|
| レシート撮影入力 | カメラ撮影で日付・店舗名・金額・品目を自動読み取り |
| 手入力／お気に入り入力 | レシート紛失時の代替、よく使う購入パターンの事前登録 |
| 自動入力 | 定期収入・定額支出の自動反映 |
| レシピ提案 | 購入食材をもとに8,000以上のレシピから提案（NHK「きょうの料理」のプロレシピも一部閲覧可、iOS版のみ） |
| 収支分析 | グラフ・カレンダーで費目別・店舗別に可視化 |
| 目標設定 | 貯金目標と進捗（「貯金箱」機能）を管理 |
| しっかりモード | 複数口座・クレジットカード管理まで対応する詳細管理モード |

**無料版と有料版の違い：** 機能面での差はほぼなく、**有料プラン（月額200円）は広告非表示のみ**が価値。全機能を無料開放してユーザー基盤（400万DL超）を広げ、広告収益＋一部の広告除去課金で収益化する軽量なマネタイズモデル。

| | 無料版 | 有料プラン（月額200円） |
|---|---|---|
| 全機能（レシート読取・レシピ提案・収支分析等） | ○ 制限なく利用可 | ○ 同様に利用可 |
| 広告表示 | レシート1枚登録するごとに広告表示 | トップ・グラフ集計・かうものメモ・カレンダー・レシート登録時など全面非表示 |
| 重要なお知らせ | 表示 | 一部は引き続き表示 |

**レシピ提案の実態：** 公式サイト・レビューのいずれにも、食材とレシピのマッチング方法についての技術的説明は一切公開されていない。公式表現も「購入食材をもとに…ランダムに提案」にとどまり、ユーザーレビューにも「機能はそこまで求めていない人向け」という声がある。**レシピ提案は"おまけ機能"の位置づけであり、精度を主役に据えた設計は競合不在**と推測される。

**示唆：** レシーピ！のマネタイズは低単価（月200円・広告除去のみ）。ヘルスケアジャンルの知見（明確なペイン解決型はサブスク単価を上げやすい）と合わせると、レシピ提案の精度自体を価値の中心に据える設計であれば、より高単価のサブスクを狙える余地がある。

#### 隙間（差別化ポイント）

1. **iOS市場の空白** — レシーピ！はAndroid限定。
2. **「自動入力（レシートOCR）」×「高精度AIマッチング」の両立**が誰もできていない。レシーピ！は自動だが提案が雑、peccoは賢いが手入力が面倒。
3. **技術的な核心課題：** スーパーのレシートは省略・店舗独自コード表記（例：「ﾄﾏﾄ 1P」）が多く、レシピDBの食材名への正規化がボトルネック。レシーピ！の提案が「ランダム」なのはこの精度を出し切れていないためと推察される。ここを作り込めれば差別化の核になる。
4. **食品ロス削減との掛け合わせ：** レシートの購入日を使い、賞味期限が近い食材を優先的に使うレシピを自動提案する設計にすると、pecco型の食品ロス訴求とも接続できる。

#### 推奨する差別化設計

「レシートOCR＋食材名の正規化辞書（スーパー独自表記対応）＋購入日ベースの消費期限管理＋AIレシピマッチング」を一体化し、iOS優先で展開。日常的な買い物習慣に乗せやすいためサブスク課金との相性が良い。

#### 個人開発上の注意点

- レシピDBを自前で用意する必要がある（クックパッドの無断クローリングはNG）。初期の献立バリエーション確保が負荷になりやすい。
- レシート印字は店舗ごとにフォーマットが異なり、OCR＋正規化の精度作り込みに開発コストがかかる。MVPは主要スーパー数社対応からのスタートが現実的。

#### レシートフォーマット調査（詳細）

**表記のばらつきの実態：** 同一商品「雪印北海道100 さけるチーズ スモーク味」を12社で購入検証した事例では、店舗ごとに表記が大きく異なった。
- セブン-イレブン：「さけるチーズスモーク味」（一部混合表記）
- LAWSON：「ﾕｷｼﾞﾙｼ ｻｹﾙﾁｰｽﾞ ｽﾓｰｸｱｼﾞ」（半角カタカナのみ）
- マルエツプチ：「雪印さけるチーズ」（フレーバー情報が欠落）
- 消費税表記も外税／内税で店舗により分かれる

**核心的なリスク：** 国内共通のJANコードは総菜・生鮮食品（野菜・肉・魚など）には付与されず、店舗独自の「インストアコード」で管理される。**レシピ提案に最も使う食材群ほど、表記が店舗ごとにバラバラで不安定**という構造的な問題がある。レシーピ！の提案が「ランダム」にとどまっている一因と推察される。

**電子レシート基盤：** 東芝テック「スマートレシート」は会員300万人・全国18,000店舗以上（スーパー利用が約6割）まで普及。ただし提供APIは小売事業者とのビジネス提携が前提のBtoB APIであり、個人開発者が単独で接続することはできない。将来の提携候補として記録に留める。

**OCR技術の選定：** Google Cloud VisionまたはAzure Computer Visionが日本語レシートに対応（AWS Textractは日本語非対応）。感熱紙の劣化・印字の薄さ・レシートの長さによって精度が左右される。

**表記ゆれの吸収手法：** 単純な文字列距離（レーベンシュタイン距離）よりサブワード分散表現（FastText等）によるベクトル類似検索の方が高精度・高速という企業事例があるが、これはGS1のJICFS商品DBを自前で保有する前提の大規模実装であり、個人開発にはオーバースペック。

**レシピDB調達の制約：** 楽天レシピAPIは無料で個人開発でも利用できるが、**利用規約で商用利用は禁止**されており、長期保存・再表示も原則不可。サブスク課金モデルの土台にはできない。クックパッドの公開APIも一般開発者には提供されていない。

#### MVP機能の絞り込み

技術・法務双方の制約を踏まえ、個人開発で現実的に組める範囲に絞る。

**MVPに含める機能**

| # | 機能 | 設計方針 |
|---|---|---|
| 1 | レシート撮影→OCR | Google Cloud Vision APIで文字抽出 |
| 2 | 食材の正規化・非食品除外 | 固定辞書やベクトルDBを自前構築する代わりに、LLM（Claude API等）にOCR結果を渡して正規化。「ﾄﾏﾄ 1P」→「トマト」等の変換を辞書メンテなしで実現し、レジ袋・割引・ポイント等の非食品行も除外 |
| 3 | 低信頼度項目のワンタップ確認 | 完全自動化を狙わず、認識しづらい項目だけユーザーに一言確認させるUIで精度不足を補う（pecco型の手入力とレシーピ型の全自動の中間） |
| 4 | 食材ベースのレシピ提案 | 固定レシピDBを持たず、LLMにその場で食材リストを渡してレシピを生成させる方式。楽天レシピ／クックパッドAPIのライセンス問題を回避でき、AI-nativeアプリのトレンドとも合致 |
| 5 | 対応店舗を2〜3チェーンに限定してスタート | 表記パターンの初期チューニング対象を絞る（例：イオン、ライフ、ヤオコーなど大手から。全国対応は後回し） |

**MVPから外す機能（v2以降）**
- 賞味期限管理・食品ロス訴求
- 家計簿的な支出管理・グラフ化
- お気に入りレシピ保存・週間献立カレンダー
- 好み学習によるパーソナライズ
- 電子レシート（スマートレシート等）との直接連携（ビジネス提携が必要なため）

**絞り込みの理由：** MVPで検証すべき核心は「レシートOCR＋LLM正規化で、入力負担を減らしつつ実用的なレシピ提案ができるか」の一点。この核心が機能してから拡張するのが個人開発のリスク管理として妥当。

#### 技術検証：LLM正規化ステップの机上プロトタイプ検証

**検証方法と限界：** 実物レシートの写真・大量サンプルはWeb検索では入手不可（実例掲載ブログは403でアクセス不可）。判明している実表記パターン（イオンの実例「ｻｹﾙﾁｰｽﾞｽﾓｰｸ25g\*2」、12社比較調査で確認された半角カナ・スペースなし表記）を踏まえて現実的な想定テストケースを構築し、LLM（Claude）による正規化を実行した。これは「LLMが省略表記を解釈できるか」という仮説の机上検証であり、「実際のOCRがどの程度きれいなテキストを出力するか」は別問題として未検証。

| 雪印ｻｹﾙﾁｰｽﾞ25g\*2 | さけるチーズ | 高 | 実在の表記パターンで確認済み |
| ﾚｼﾞ袋(有料)／ﾎﾟｲﾝﾄ値引 | 除外（非食品） | 高 | |

**わかったこと**

1. 典型的な生鮮食品の省略表記は、LLMなら固定辞書なしで高い確信度で解釈できる（テスト対象の食品系アイテムの大半が高信頼度）。当初の仮説（LLM正規化は有効）を支持する結果。
2. 本当のリスクは「同音異義的な省略」がOCR誤読と重なるケース。「ｻｹ」（鮭／酒）のように、周辺文字（"ｷﾘﾐ"＝切り身）が正しく読めて初めて正確に判定できる例がある。**OCR精度とLLM正規化精度は独立ではなく直列で効いてくる**という設計上の重要な示唆。
3. 「食材」と「食品全般」（飲料・菓子など）の境界線をどう扱うかはMVPの仕様決定事項として残る。
4. 量・単位表記（100g、1/2、3ホン等）を活かした分量ベースの提案は将来機能とし、MVPでは食材名抽出のみに絞るという結論を補強。

**次の検証ステップ（Web調査の範囲外）：** 実際にイオン・ライフ・ヤオコー等でレシートを数十枚収集し、Google Cloud Vision APIで実OCRをかけて出力の荒れ具合を確認したうえで、その生OCR結果をLLMに正規化させて実際の成功率を計測する必要がある。これには実物データとAPI実行環境が必要なため、本リサーチでは机上検証にとどめた。

### 4-6. 方向転換：「気分ベースの食べ物提案アプリ」（レシピに限定しない）＋レシート読み取りはサブ機能

ユーザーの構想変更を受けた再評価。「レシピ提案」から「気分に応じてコンビニ・惣菜・レシピを横断提案する食べ物提案アプリ」へ主軸を変更し、レシート読み取りは主機能ではなく差別化のためのサブ機能（学習シグナル）と位置づける。

#### 既存の「気分ベース提案」サービスとの比較

| サービス | 対象領域 | 気分入力の例 |
|---|---|---|
| おいしい健康 | 自炊レシピ（管理栄養士監修×AI） | 「今日は和食の気分」「お腹の具合が良くないので、さっぱりした食事」に対応済み |
| あすけん（AIこんだて提案・β） | 自炊レシピ | 栄養士キャラ「未来さん」とのチャットで献立提案 |
| ぐるなび「UMAME!」 | 外食（飲食店検索） | 生成AIで気分・ニュアンスに応じた店舗提案 |
| 食べログ（2026年新機能） | 外食 | 対話型AI検索を搭載予定 |
| コンビニ公式アプリ（セブン、ローソン等） | コンビニ商品 | クーポン・ポイント中心で、気分ベースの提案機能はなし |

**白地：** 「自炊」と「外食」はそれぞれ別々に気分ベース提案が存在するが、「自炊する気力がないので、コンビニか惣菜で済ませたい」という選択肢横断の悩みに応えるサービスは確認できなかった。気分入力（例：「さっぱりしたものが食べたい」）に対し、レシピだけでなくコンビニ商品・惣菜も並列で提案するアプリは競合不在。

#### 技術的な実現性

- コンビニ各社が個人開発者向けに商品データAPIを公開している事実は確認できず、特定店舗のリアルタイム在庫や実在の商品名を断定的に提示するのは困難。
- 現実的なMVPでは**カテゴリ単位の提案**（「サラダチキン系」「海藻サラダ」「冷やし中華」等）にとどめ、実在の特定商品を断定しない設計が安全。
- 具体的な商品訴求をしたい場合は、将来的にコンビニ各社や惣菜チェーンとの提携が必要（レシーピ！のNHK「きょうの料理」連携のように、公式コンテンツ提携で信頼性を担保する道もある）。

#### レシート機能の位置づけの再設計

従来案（4-5）ではレシートが主機能だったが、本案ではレシートは**サブ機能＝学習シグナル**に役割が変わる。これにより、4-5で確認した技術リスク（生鮮食品は店舗ごとに表記がバラバラで正規化が難しい）の影響が小さくなる。今回の用途では厳密な食材名の特定は不要で、「揚げ物系」「麺類」「サラダ系」といった大まかなカテゴリ分類で足りるため、精度要求が下がる。

**レシートを使った差別化の具体案：**
1. **食履歴の自動蓄積** — スキャンだけで「最近何を食べたか」が手入力なしで溜まる（他の食事管理アプリは手入力や写真判定が主流で摩擦が大きい）
2. **提案の重複回避** — 直近で買ったものを提案候補から自然に除外
3. **能動的な気分提案** — 「今週揚げ物が続いているので、今日はさっぱり系はいかがですか？」のように、気分入力なしでもレシート履歴から先回り提案できる（チャット依存のあすけんにはない体験）

#### 総合評価

①既存競合が手を出していない「選択肢横断の気分提案」という白地、②レシートを厳密なマッチングでなく履歴学習として使うことで技術リスクが下がる、という2点で筋が良い設計と評価する。

#### 技術検証：自然言語→カテゴリ判定と、コンビニ・惣菜への接続可能性

**惣菜・コンビニ側のカテゴリ体系（既存の公開情報で代替可能）：** 日本標準商品分類では惣菜が8カテゴリに整理されている（煮物類／焼き物類／炒め物類／揚げ物類／蒸し物類／和え物類／米飯類／その他調理食品）。コンビニ側もレビューサイト（もぐナビ等）で「おにぎり」「惣菜」「弁当」「麺類」「スイーツ」等、類似のカテゴリ構造が業界内で共通認識として使われている。これは無料の公開情報であり、MVPの分類辞書の土台にできる。

**自然言語→カテゴリ判定の机上テスト：** 上記のカテゴリに「温冷」「さっぱり/こってり」「辛さ」「ボリューム感」「和洋中」等の軸を加えて気分入力を分類した。

| 気分入力 | 判定される軸 | 対応カテゴリ | 信頼度 |
|---|---|---|---|
| 「さっぱりしたものが食べたい」 | さっぱり系／冷 | 和え物類・酢の物、冷やし中華、海藻サラダ | 高 |
| 「こってり系でガッツリ食べたい」 | こってり系／ボリューム大 | 揚げ物類、から揚げ弁当 | 高 |
| 「疲れたから温かいものが欲しい」 | 温／汁物 | 煮物類、おでん、スープ | 高 |
| 「夏バテで食欲がない」 | 軽め／喉越し | そうめん系、冷やし中華、酢の物 | 高 |
| 「ヘルシーに済ませたい」 | 低カロリー／野菜多め | 蒸し物類、サラダチキン | 高 |
| 「辛いものが食べたい」 | 辛味 | 中華系、麻婆・辛麺 | 中 — 惣菜協会の8分類に「辛さ」軸がなく、独自軸の追加が必要 |
| 「元気を出したい」 | 感情起点（コンフォート欲求） | こってり系／甘味系どちらもあり得る | 低 — 感情語彙は一意に定まらず、聞き返しが必要 |
| 「なんでもいいけどお腹すいた」 | 判定材料なし | フォールバック提案（人気ランキング等）が必要 | 低 |

**わかったこと：** 味・温度・ボリュームを含む気分表現は高精度でカテゴリ化できるが、「元気を出したい」のような感情語彙は一意に定まらず、カテゴリ判定だけでなく時々ユーザーに一言聞き返す会話設計（例：「こってり系と甘いもの、どちらの気分に近いですか？」）が必要になる。

**カテゴリから具体的な商品への接続（技術的な壁）：** カテゴリ判定は可能だが、実在の店舗商品名まで正確につなげるのは個人開発では現実的ではない。
- コンビニ商品を体系的にカバーする商品データベースAPI（IMD社の食品栄養データベース、40万件以上でコンビニ・ファミレス等をカバー）は存在するが、**ライセンス料が年額200万円〜**で個人開発の予算を大きく超える。
- 「コンビニDB」のような商品情報サイトも存在するが、公式提携なしの第三者サイトである可能性が高く、スクレイピング等での利用は著作権・利用規約上のリスクがある。
- コンビニ各社が個人開発者向けに商品APIを公開している事実は確認できなかった。

**MVP設計への反映：**
- 提案は「カテゴリ＋属性」レベルにとどめる（例：「揚げ物系のガッツリ惣菜がおすすめです。コンビニのから揚げコーナーか、スーパーの揚げ物惣菜を見てみてください」）
- 実在の商品名を断定的に出さない（法的リスク回避、店舗差異への対応）
- 感情語彙で味の軸が定まらない場合は、一言だけ聞き返す会話設計を入れる
- 将来的に特定商品まで踏み込みたい場合は、コンビニ各社・惣菜チェーンとの個別提携を検討（レシーピ！のNHK「きょうの料理」連携のような形）

#### 技術検証：近隣店舗検索とメニュー取得の実現性

「近くの店舗を探す」ことと「その店舗の具体的なメニュー内容を取得する」ことは別問題であり、後者は難易度が大きく異なる。

**近隣店舗の位置検索：** 技術的に解決済みの領域。本ワークスペースの`apps/web`のCafeFinderがOverpass API（OpenStreetMap）で近隣カフェ検索をすでに実装しており、同様の仕組みでコンビニ・飲食店の位置情報も取得可能。Google Places APIのNearby Searchも選択肢になる。

**具体的なメニュー内容の取得：** 個別に見て困難。

| API | 現状 | メニュー情報の粒度 |
|---|---|---|
| 食べログAPI | 2014年に完全終了。現在は提供なし | 取得不可 |
| ぐるなびAPI | 2021年6月に無料提供終了。現在は法人限定・有料 | 個人開発者は利用不可 |
| ホットペッパーグルメAPI | 個人開発でも無料利用可 | 店舗単位の情報のみ（店名・住所・エリア・ジャンル・予算・紹介文・写真1枚）。個別の料理名・価格までは取得不可と公式に明記 |
| Google Places API（新版） | 有料従量課金（$17/1,000件、月$200無料枠あり） | "businessMenus"フィールドで料理名・説明・価格を構造化取得できる可能性はあるが、対応店舗数は限定的で網羅性は保証されない |

**コンビニについてはさらに厳しい。** そもそも「メニュー」という概念がなく飲食店向けAPIの対象外。商品データを体系的に持つのは前述のIMD社データベース（年額200万円〜）くらいで、個人開発で扱える手段は事実上ない。

**MVP設計への反映（更新）：**
1. 位置情報で近隣のコンビニ・飲食店をリスト表示（Overpass／Google Places）
2. 気分から判定したカテゴリ提案（例：「揚げ物系のガッツリ系がおすすめです」）を組み合わせる
3. 飲食店については、Google Places APIのbusinessMenusが取得できれば補助的に表示し、取れない店は非表示。または食べログ・ぐるなびの店舗ページへ外部リンクし、メニュー確認はユーザーに委ねる
4. コンビニは商品名を出さず「近くのコンビニ○件」＋カテゴリ提案のみにとどめる
5. 結果として、「AIが具体的な商品名まで教えてくれる」体験は個人開発では作り込めず、**「気分に合うジャンルを教えてくれて、あとは近くの店で選ぶ」という体験が現実的な着地点**になる

#### 技術検証：「おすすめ店舗」推薦機能の実現性

メニュー内容の取得より、店舗単位の推薦（ジャンル・評価・口コミの雰囲気で「どの店が良いか」を示す）は実現性が高い。

**飲食店の推薦は現実的：** 個別メニューではなく「ジャンル」「評価」「距離」「口コミの雰囲気」で構成できる。

| データ | 取得元 | 内容 |
|---|---|---|
| ジャンル分類 | ホットペッパーAPI「ジャンルマスタ」／Google Places `primaryType` | 和食・中華・ラーメン・居酒屋等の分類が取得可能 |
| 評価・距離・営業時間 | Google Places API（Pro階層） | 評価スコア、営業中か否か、距離を取得可能 |
| 口コミの雰囲気 | Google Places API（Enterprise階層） | 上位5件の口コミ本文に加え、Googleが生成したAI要約（口コミサマリー）を取得できる新機能が2025年に追加されている。気分マッチングにそのまま利用可能 |

気分マッチングの設計イメージ：「さっぱり系」判定→ジャンルを和食・サラダ系に絞り込み→評価上位を提示→AI口コミ要約に「あっさり」「さっぱり」等の言及があれば優先度を上げる、という多段フィルタが技術的に組める。

**コンビニは推薦の中身が薄い。** 店舗ごとの差別化データ（品揃え・混雑状況等）が取得できないため、「推薦」というより「近い順に一覧を出す」「好きなチェーンを優先する」程度にとどまる。

**料金体系（2025年3月改定）：** Google Places APIは階層制。Essentials（ID・店名・緯度経度等）は月10,000件無料、Pro（営業時間・評価・写真等）は月5,000件無料、Enterprise（口コミ等）は月1,000件無料。口コミ活用は無料枠が少なく、同一エリアの検索結果を一定時間キャッシュする実装で呼び出し回数を抑える工夫が必要。

**マネタイズとの整合性（重要）：** 無料で使える日本の飲食店API（ホットペッパー、楽天レシピ）は軒並み商用利用が禁止されている。サブスク課金モデルで収益化するなら、無料枠のAPIをそのまま組み込むのは規約違反リスクがある。一方、Google Places APIは最初から有料の商用サービスであり、課金さえすれば商用アプリへの組み込みに問題はない。
- プロトタイプ検証・無料版：ホットペッパーAPI（ジャンル・店舗情報の実験に）
- 本番のサブスク課金アプリ：Google Places APIを主軸に据える（コストはユーザー課金でカバーする前提）

**結論：** 「気分に合うジャンルの、評価が良く、口コミの雰囲気もマッチする店を教えてくれる。ただし店内の具体的な品目までは店で確認する」という体験が、実現可能性とコストのバランスが取れた設計となる。

## 5. マネタイズモデルの比較（未定とのことなので選択肢を整理）

| モデル | 特徴 | 個人開発との相性 |
|---|---|---|
| 広告収益（無料＋広告） | DL数を伸ばせば収益化。単価は低い | DL数が出るジャンル（暇つぶし系・ツール系）向き。1人運用でも回しやすい |
| サブスクリプション課金 | 継続収益が作れ、市場全体の成長率も高い（アプリ内課金市場CAGR26.2%） | 明確な継続ペイン（健康管理、ニッチ業務効率化等）があるアプリ向き。開発・運用の手間は増える |
| 買い切り・単発課金 | シンプルな収益モデル、実装も分かりやすい | ツール系・専門機能アプリ向き。収益の天井が低くなりやすい |

**推奨：** 個人開発かつ継続的な収益を狙うなら、明確なペインを持つニッチ市場×サブスクの組み合わせが2026年の市場成長トレンドと最も整合的。ただしDL数を稼ぎやすい大衆向けツールなら広告モデルも十分現実的。

## 6. 総合所感（狙い目の方向性）

1. **「ニッチ×AI」「ニッチ×トレンド」の掛け合わせ**が個人開発の基本戦略。汎用ツール（ToDo、ChatGPTラッパー等）は避ける。
2. **ヘルスケア・フィットネスの特定種目特化**は、市場成長率・ユーザーの健康意識の高さから狙い目。
3. **特定業種・職種に特化したAIアシスタント**（士業、美容系、飲食店など）は、汎用AIチャットの飽和を避けつつニーズが明確。
4. マネタイズは「明確な継続ペインがあるならサブスク」「DL数で稼ぐならツール系＋広告」で使い分ける。
5. 2026年は「作る」より「届ける」（SNS発信、コミュニティ形成、ASO等）の設計が成否を分けるため、開発と並行して発信チャネルの計画も持つことを推奨。
